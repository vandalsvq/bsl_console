Заголовок: **Потребление памяти консоли в поле 1С: разбор источников и оптимизация**

---

Повод — встраивание консоли в прикладное решение: первая инициализация 300–400 МБ, каждый следующий
экземпляр 200–300 МБ, при закрытии формы платформа память не отдаёт. Разобрали расход по частям на
полевом стенде, одну утечку нашли и закрыли. Ниже — что намерили, что уже сделано и куда идём дальше.

Документы трека: `research.md` (журнал измерений), `plan.md` (план и решения), `result.md` (итог).

## Стенд и метод

Платформа 8.3, тонкий клиент, файловая база, ветка `webpack` (Monaco 0.55.1), сборка `build:pack`.
Память снималась по процессам платформы (Working Set / Private bytes) на каждом шаге сценария.
Дополнительно собиралась временная диагностическая сборка со счётчиками, доступными прямо в поле:
число моделей и редакторов Monaco, размер `bslMetadata`, `contextData`, DOM-узлы, счётчик событий.

Правило, выведенное по ходу: полевой замер засчитывается только с **нормировкой на счётчик** (правки,
вызовы подсказок, обращения за метаданными). Working Set в этом движке скачет на ±150 МБ сам по себе,
и без нормировки «подтверждается» любая версия.

Наблюдение по устройству: **отдельного процесса под webview нет** — при открытии консоли ни одного
дочернего процесса не появляется, редактор живёт внутри процесса клиента `1cv8c.exe`. Поэтому память
полностью возвращается только с закрытием клиента, а рычага «прибить процесс рендерера» не существует.

## Результат: утечка в `calculateDiff()` найдена и исправлена

`src/editor.js` — функция висит на `onDidChangeModelContent` (дебаунс 50 мс), то есть срабатывает
практически на каждое изменение текста, и каждый раз создавала новую `TextModel` с полной копией
оригинала:

```js
window.diffEditor.setModel({
  original: monaco.editor.createModel(window.editor.originalText),
  modified: window.editor.getModel()
});
```

Прежняя модель не удалялась — Monaco модели сам не диспозит. Условие срабатывания: задан оригинальный
текст (`setOriginalText`) и включены diff-декорации, то есть штатный режим с отслеживанием изменений.

A/B двумя сборками, отличие ровно в этом изменении. Сценарий: N циклов «символ → точка → `Esc` →
два `Backspace`» с паузами.

| | без исправления | с исправлением |
| --- | --- | --- |
| правок текста | 31 | 81 |
| моделей Monaco: до → после | 3 → **34** | 2 → **2** |
| Working Set: до → после, МБ | 666.4 → 793.0 | 722.7 → 668.7 |
| Private bytes: до → после, МБ | 611.6 → 753.1 | 667.3 → 604.3 |
| Δ памяти | **+126.6 МБ** | **−54.0 МБ** |

Утёкших моделей ровно столько же, сколько правок. Вес копии равен весу открытого модуля: 312 тыс.
символов ≈ 4.5 МБ на модель с токенизацией. За рабочий день это гигабайты, и закрытие формы их не
возвращает.

Исправление: не пересоздавать `original`-модель, когда пересоздавать нечего — diff пересчитается сам
по изменению `modified`-модели; при реальной смене оригинала прежняя модель диспозится. Заодно сняты
три временные модели, создававшиеся только ради `getFullModelRange()`: `selectedText()`,
`insertLine()`, `generateSnippetEvent()`.

Проверено: `npm test`, `npm run build:test` + `npm run test:mocha` (201/201), `npm run check:workers`,
браузерный пробник (300+50+100+200 правок, 5 × `setText`, 3 × вкл/выкл сравнения, 50 × подсказок —
моделей остаётся 2; до исправления росло до 6 и дальше), полевой A/B выше.

В Chrome эта утечка почти не видна — модели шарят строки, GC работает исправно, на 120 срабатываний
прирост heap 3.5 МБ. Ловится только полевым замером.

## Что проверено и оказалось ни при чём

- **Метаданные.** За 7 обращений к разным объектам 1С прислала 65 тыс. символов, `window.bslMetadata`
  вырос с 500 169 до 528 093 символов, то есть на 56 КБ. Дедупликация запросов в `requestMetadata`
  работает корректно.
- **Сами подсказки.** 40 глобальных вызовов (`CTRL+Пробел`) — −12 МБ, 80 по платформенным типам
  (`Массив.`, `ТаблицаЗначений.`) — +9 МБ, то есть шум.
- **Быстрые правки.** 20 секунд автоповтора `Enter` — −27 МБ: дебаунс схлопывает очередь изменений
  в считанные вызовы. Утечку даёт обычный ручной набор с паузами.
- `contextData`, `customHovers`, число DOM-узлов по ходу работы не растут.

## Что проверено и закрыто

### 1. Возврат памяти при закрытии формы — не работает

Платформа отдаёт контекст поля не полностью: после рабочей сессии в процессе клиента остаётся
450–880 МБ. Проверяли, можно ли снести контекст самим: в `ПередЗакрытием` формы подряд вызывались
`__mmDispose()`, `Документ.body.innerHTML = ""`, `Документ.location.replace("about:blank")`,
`defaultView.location.replace("about:blank")` и обнуление реквизита `HTML`, каждый вызов писал
результат в лог-файл (молчаливая `Попытка` не отличает «сработало» от «движок не умеет»).

**Все пять способов движок принимает без исключения. Памяти это не возвращает** — осело ровно
столько же, сколько без сноса.

Контрольная сборка-пустышка (та же обёртка epf и та же форма, но в макете страница в десять строк
с заглушками моста) за 5 циклов «открыл — закрыл» набирает **2.9 МБ на цикл** против **81 МБ**
у консоли. Платформа, обёртка и сам WebView почти ничего не держат — держит содержимое поля.

Ряд циклов в одном клиенте: пол после каждого закрытия растёт на 36 МБ (циклы 2–5), затем на 16
(циклы 6–8) — смесь реального осадка и высокой воды аллокатора, а не чистая линейная утечка.
Первая инициализация консоли стоит клиенту 300–400 МБ безвозвратно.

### 2. Обрезка контрибов Monaco — 2.1 % бандла

Свой узкий entry вместо `edcore.main`: из ~65 контрибов оставлены только используемые консолью
(по списку `editor.action.*` из кода). Первые заходы не дали ничего, и причина оказалась
интересной:

> `basic-languages/xml/xml.js` — 8 КБ правил грамматики, перед которыми **73 импорта, тянущих весь
> редактор со ВСЕМИ контрибами**. Так monaco-editor 0.55 отдаёт ESM basic-languages. Мы подключаем
> XML ради подсветки в режиме сравнения — и этим полностью обнуляем узкий entry `edcore.main`.

После выноса грамматики XML к себе (только `conf` + `language`, без импортов) обрезка заработала:
`stickyScroll`, `rename`, `inspectTokens`, `colorPicker`, `codelens`, `inlayHints` из сборки ушли.
Экономия — **225 КБ из 10.5 МБ**. С учётом того, что память не пропорциональна объёму кода, в поле
это единицы мегабайт.

### 3. Ленивые словари — около нуля

Потолок слоя известен точно: 56 МБ, 14 % экземпляра. Замер самого приёма (одни и те же данные,
`bslGlobals`, 2.00 МБ символов JSON; браузер перезапускается на каждый вариант):

| вариант | RSS над пустой страницей |
| --- | --- |
| объектный литерал (как сейчас) | +20.1 МБ |
| строка JSON, не разобрана | +18.7 МБ |
| строка JSON + `JSON.parse` | +16.5 МБ |
| gzip+base64 (0.53 МБ), не распакован | +10.3 МБ |

Причина в кириллице: строка JSON хранится по два байта на символ, поэтому 2.00 МБ данных — это
4 МБ строки, столько же, сколько весит готовый объект. **Неразобранная строка стоит как литерал —
откладывать нечего.** Экономит только сжатое хранение, примерно вдвое, и ровно до первого
обращения; для консоли, где подсказки и есть основной сценарий, это выигрыш на минуту.

Отделить описания от структуры тоже не выход: текстовые поля (`description`, `returns`) — лишь
24.5 % словаря, остальное имена, сигнатуры, параметры, типы.

## Итог

Из 400 МБ экземпляра **61 % — загрузка бандла Monaco ещё до создания редактора**. Это не режется
ни обрезкой контрибов, ни работой со словарями; дальше — только вмешательство в сам Monaco, что
выходит за рамки консоли.

Что реально даёт эффект — на стороне интеграции:

- **выключить автозагрузку синтакс-помощника** по умолчанию: −763 МБ на экземпляр;
- **не плодить экземпляры** — переиспользовать одну форму: ~180–200 МБ за каждый несозданный.

Мелочи, оставшиеся в коде редактора: чистить `contextData` при `setText`, экспортировать
`disposeConsole()` (ради предсказуемости, не ради мегабайт — возврата памяти нет) и выгрузку
справки `disposeHelp()` (−178 МБ, когда справка загружена).

Осталось без ответа: почему открытый модуль 509 КБ стоит в поле 131 МБ против 21 МБ в Chrome.

## Отдельно: умолчание для синтакс-помощника

Автозагрузка справки стоит 763 МБ на экземпляр — больше, чем всё остальное вместе взятое, и в нашей
форме она включена по умолчанию. Для сценариев, где справкой не пользуются, это чистые потери.
Вариант: грузить сразу только `shlang` (90 КБ), остальные пакеты — по первому обращению. Это решение
о поведении по умолчанию, а не баг, поэтому вынесено отдельным пунктом.
