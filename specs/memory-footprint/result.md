# memory-footprint: результат

Итог трека одной страницей: что сделано, какими числами это подтверждено, что уходит в upstream,
что остаётся на нашей стороне и что ещё открыто. Подробности измерений — в
[`research.md`](research.md), текст задачи автору — в [`issue.md`](issue.md).

## 1. С чего начали

Интеграция в PrintWizard: первая инициализация консоли 300–400 МБ, каждый следующий экземпляр
200–300 МБ, при закрытии формы память не возвращается.

## 2. Что оказалось на самом деле

| Статья | Цена в поле 1С | Комментарий |
| --- | --- | --- |
| экземпляр консоли, пустой | +329 МБ | это и есть наблюдавшиеся «300–400 МБ» |
| открытый модуль 509 КБ | +131 МБ | в 258 раз больше самого текста |
| **правки текста (утечка)** | **4.1 МБ на правку** | найдено и исправлено |
| синтакс-помощник, если грузится | +763 МБ | у нас включён по умолчанию |
| параллельный экземпляр | ~180 МБ | второй и далее дешевле первого |
| осело после закрытия всех форм | 655–884 МБ | платформа не сносит контекст поля |

Ключевое по устройству: **отдельного процесса под webview нет** — редактор живёт внутри
`1cv8c.exe`, поэтому память полностью возвращается только со смертью клиента.

## 3. Что сделано

### 3.1. Исправлена утечка diff-моделей (идёт в upstream)

`calculateDiff()` вызывался на каждое изменение текста и каждый раз создавал новую `TextModel`
с полной копией оригинала, не удаляя прежнюю. Теперь модель переиспользуется, а при реальной смене
оригинала прежняя диспозится. Плюс сняты три временные модели, создававшиеся ради
`getFullModelRange()` в `selectedText()`, `insertLine()`, `generateSnippetEvent()`.

Полевой A/B (§2.0.1 `research.md`): без исправления 31 правка → +31 модель → **+126.6 МБ**;
с исправлением 81 правка → моделей по-прежнему 2 → **−54.0 МБ**.

Гейты: `npm test`, `build:test` + `test:mocha` 201/201, `check:workers`, браузерный пробник,
полевой A/B.

### 3.2. `tools/make_epf.ps1` научился находить макет с HTML

Имя макета жёстко предполагалось `single`; у обёртки автора он называется `src`. Теперь макет
ищется по содержимому (первые байты — `<!doctype html>`/`<html>`), так что скрипт работает с обеими
обёртками.

## 4. Что предлагается сделать дальше

### На стороне интеграции — самый крупный рычаг

| # | Что | Эффект |
| --- | --- | --- |
| B0 | Выключить автозагрузку синтакс-помощника по умолчанию | **−763 МБ на экземпляр** |
| B1 | Один экземпляр консоли на приложение вместо нескольких | ~180 МБ за каждый несозданный |
| B3 | Проверить, сносит ли контекст переустановка содержимого поля перед закрытием формы | до 655–884 МБ, если платформа отрабатывает |

### В коде редактора

| # | Что | Эффект |
| --- | --- | --- |
| A2 | Ленивые словари (`bslGlobals` и соседи — парсить при первом обращении) | до −19 МБ (замер в Chrome) |
| A4 | Чистить `contextData` и соседние кэши при `setText`/смене модели | останавливает медленный рост |
| A5 | Экспортировать `disposeConsole()` | предсказуемое состояние перед закрытием формы |
| A7 | Экспортировать выгрузку справки (`disposeHelp()`) | −178 МБ, когда справка загружена |

Отдельный вопрос без ответа: почему модуль 509 КБ стоит в поле 131 МБ, тогда как в Chrome — 21 МБ.
Здесь может лежать ещё один крупный рычаг.
