# memory-footprint: из чего складывается потребление памяти консоли

Исследование 22.08.2026. Повод — интеграция в PrintWizard: первая инициализация консоли даёт
300–400 МБ, каждый следующий экземпляр 200–300 МБ, при закрытии формы 1С память не возвращает.

Статус: **исследование** (не спека). Ниже — измеренные числа, разбор источников и гипотезы
с оценкой эффекта. Изменений в коде по итогам ещё не принято.

> **Справка 1С (HBK) в сценарии PrintWizard не используется** — файл `.hbk` в редактор не подаётся.
> Её замеры оставлены ниже справочно (§2.3): без загруженного файла подсистема справки стоит только
> своего кода в бандле — 0.3 МБ из 10.5 (модули `src/help/*` 0.2 МБ + строки воркеров `help_worker`
> 65 КБ и `index_worker` 39 КБ), то есть ориентировочно 1–2 МБ памяти; worker'ы без файла не
> стартуют, UI не создаётся. Из списка рычагов справка исключена.
>
> Полевой замер (§2.0) уточнил цену справки, когда её всё-таки грузят: **763 МБ** в поле 1С против
> 214 МБ в Chrome. Для тех, кто справкой пользуется, это самая крупная отдельная статья расхода.

## 1. Стенд и метод

- Сборка `build:pack` (v0.5.5 + наша ревизия формы), Chrome headless, Windows 11.
- Метрики: Working Set всех процессов браузера (`--type=renderer` отдельно) + JS heap страницы и
  воркеров через CDP (`Runtime.getHeapUsage` после `HeapProfiler.collectGarbage`).
- Пробники (не в репозитории, лежат в scratchpad сессии): `mem_probe.js` (этапы жизненного цикла),
  `multi_probe.js` (несколько экземпляров), `leak_probe.js` (рост моделей), `release_probe.js`
  (что возвращается без закрытия документа), `heap_report.js` (разбор heap-снимка).
- Chrome — нижняя оценка: WebKit «Поля HTML документа» тяжелее, но профиль расходов тот же.
- **Полевой стенд (22.08.2026):** платформа 8.3.x, тонкий клиент `1cv8c.exe`, файловая база,
  `Рабочие\console-monaco-0.55.epf` (v0.5.5 + наша ревизия формы, сборка `build:pack`).
  Метрики снимались скриптом `bsl_console_test\mem_step.ps1` (WorkingSet / PrivateBytes по всем
  процессам платформы, лог в `mem_1c_log.csv`); шаги выполнял мейнтейнер, замер после каждого шага.

## 2. Что намерили

### 2.0. Полевой замер в 1С (главный результат)

Ключевое наблюдение по устройству: **отдельного процесса под webview нет** — при открытии консоли
не появляется ни одного дочернего процесса, весь редактор живёт внутри `1cv8c.exe`. Значит рычага
«убить процесс рендерера» не существует в принципе, и вся память возвращается только со смертью
клиента (проверено: закрытие клиента вернуло системе все 620 МБ).

**Прогон 1 — со включённой автозагрузкой синтакс-помощника** (реквизит формы
`ЗагружатьСинтаксисПомощникПриОткрытии`, в нашей рабочей epf включён по умолчанию):

| Момент | WS клиента | Private | Δ к базе (WS) |
| --- | --- | --- | --- |
| 1С запущена, консоль не открыта | 155.3 | 100.8 | — |
| консоль открыта, пик | 1425.2 | 1503.1 | +1270 |
| консоль открыта, устоялось (20 с) | 1246.9 | 1285.2 | **+1092** |
| форма закрыта | 607.2 | 549.3 | +452 |
| +60 с после закрытия | 606.8 | 549.6 | +452 (не меняется) |

**Прогон 2 — автозагрузка справки выключена, клиент перезапущен** (это сценарий PrintWizard):

| Момент | WS клиента | Private | Δ к предыдущему |
| --- | --- | --- | --- |
| 1С запущена, консоль не открыта | 154.0 | 103.8 | — |
| консоль открыта, ничего не вводили | 482.8 | 427.1 | **+328.8** |
| загружен модуль 509 КБ / 2121 строка | 614.1 | 546.7 | **+131.3** |
| поработали ~2 мин (подсказки, правки, поиск) | 1214.2 | 1237.4 | **+600.1** |
| простой 70 с | 1211.9 | 1233.4 | −2.3 (сборки нет) |
| форма закрыта | 1038.4 | 1073.9 | −173.5, осело **+884.4** к базе |
| консоль открыта второй раз | 1142.5 | 1165.5 | +104.1 |

**Параллельные экземпляры** (в одном клиенте, поверх предыдущего состояния):

| Форм открыто | WS | Private | Прирост (Private) |
| --- | --- | --- | --- |
| 1 | 1142.5 | 1165.5 | — |
| 2 | 996.2 | 984.4 | −181 (сработала сборка мусора) |
| 3 | 1220.9 | 1210.8 | +226 |
| 4 | 1325.8 | 1343.1 | +132 |
| все закрыты | 829.1 | 759.2 | осело **+655** к базе |

Что из этого следует:

1. **Цена одного экземпляра в поле — 329 МБ** (без справки, пустой редактор). Это ровно то, что
   наблюдалось в PrintWizard («300–400 МБ на первую инициализацию»). В Chrome тот же бандл стоит
   ~100 МБ — WebKit «Поля HTML документа» дороже примерно втрое.
2. **Синтакс-помощник стоит 763 МБ** (1092 − 329). Одна галка в настройках снимает 70 % расхода.
3. **Реальный модуль стоит 131 МБ** — в 258 раз больше самого текста (509 КБ) и в 6 раз дороже, чем
   в Chrome (+21 МБ на такой же модуль).
4. **Два часа работы не нужны: +600 МБ набегает за две минуты правок.** Это больше, чем открытие
   консоли и загрузка модуля вместе. Простой ничего не возвращает (−2 МБ за 70 с) — значит на
   объекты держатся живые ссылки, это утечка §3.1, а не отложенная сборка. При этом под давлением
   аллокаций (открытие ещё одной формы) движок всё-таки собрал 181 МБ — то есть часть роста
   собираемый мусор, но собирается он только когда прижмёт.
5. **Закрытие формы возвращает не всё и тем меньше, чем дольше работали:** после «пустого» открытия
   вернулось 640 МБ и осело 452; после рабочей сессии вернулось 174 МБ и осело **884**. Это и есть
   «1С не освобождает память при закрытии консоли».
6. **Параллельный экземпляр — ~180 МБ** (экземпляры 3 и 4 дали 359 МБ на двоих). Второе открытие
   после закрытия — всего +104 МБ: код бандла и словари переиспользуются, платформа не пересоздаёт
   контекст с нуля.

### 2.0.1. Полевой A/B по утечке diff-моделей (22.08.2026)

Две диагностические сборки от одного шаблона epf, отличие ровно в одном изменении кода
(`calculateDiff`). В обе добавлен временный счётчик (`CTRL+ALT+M` вставляет в текст отчёт:
размер `bslMetadata`, число моделей/редакторов Monaco, `contextData`, DOM, счётчик событий).
Сценарий одинаковый: чистый клиент → открыть → загрузить модуль 312 тыс. симв. → N циклов
«символ → точка → Esc → два Backspace» с паузой (важно: дебаунс 50 мс, быструю долбёжку он
схлопывает).

| | без фикса | с фиксом |
| --- | --- | --- |
| правок текста (`EVENT_CONTENT_CHANGED`) | 31 | 81 |
| моделей Monaco: до → после | 3 → **34** | 2 → **2** |
| WS: до → после, МБ | 666.4 → 793.0 | 722.7 → 668.7 |
| Private: до → после, МБ | 611.6 → 753.1 | 667.3 → 604.3 |
| Δ памяти | **+126.6** (+141.5 private) | **−54.0** (−63.0 private) |
| цена одной правки | **4.1 МБ** | 0 |

Утёкших моделей ровно столько же, сколько правок (31 → +31). Цена копии равна весу открытого
модуля: 312 тыс. символов → ~4.5 МБ на модель с токенизацией. В пересчёте на равное число правок
сборка без фикса набрала бы **+331 МБ на 81 правку** — это и есть «+600 МБ за две минуты работы»
из §2.0.

Побочные наблюдения того же прогона:

- **Метаданные почти ничего не стоят.** За 7 обращений к разным объектам 1С прислала 65 тыс.
  символов, `bslMetadata` вырос с 500 169 до 528 093 симв. (+56 КБ). Версия «виновата обвязка
  метаданных» проверена и снята.
- **Правки без пауз не текут.** 20 секунд автоповтора Enter дали −27 МБ: дебаунс схлопывает
  очередь изменений в считанные вызовы. Утечку даёт обычный ручной набор.
- **Подсказки сами по себе не текут:** 40 глобальных (`CTRL+Пробел`) — −12 МБ, 80 по
  платформенным типам (`Массив.`, `ТаблицаЗначений.`) — +9 МБ, то есть шум.
- В Chrome эта утечка почти не видна (модели шарят строки, GC работает): на 120 вызовов
  подсказок heap растёт на 3.5 МБ. Полевой стенд обязателен — браузерных пробников мало.

| Экземпляр | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- |
| прирост, МБ | 180 | 162 | 148 | 151 |

Профиль совпадает с наблюдением в PrintWizard: первый дороже (греются общие структуры), дальше

### 2.3. Справка 1С (HBK)

| Этап | Рендереры | JS heap |
| --- | --- | --- |
| до загрузки | 424 МБ | 33 МБ |
| shlang + shcntx + shquery + dcsui | 638 МБ (пик 706) | 66 МБ |
| после `helpService.dispose()` | 459 МБ | 66 МБ |

**Справка стоит ~214 МБ устойчиво (пик +330 МБ)**, и `dispose()` сервиса возвращает **178 МБ**:
пакеты и индексы живут в worker'ах, terminate их освобождает. Наружу (на `window`) этот dispose
сейчас не выведен — 1С не может освободить справку, не закрыв форму.

### 2.4. Из чего состоят базовые ~100 МБ

Три диагностические сборки, замер одним и тем же пробником:

| Вариант | Бандл | Прирост памяти | JS heap |
| --- | --- | --- | --- |
| только Monaco + грамматика/темы BSL (entry `boot.js`, словари заглушены, редактор не создаётся) | 5.2 МБ | **+44 МБ** | 8 МБ |
| наш редактор целиком, словари заглушены (`bslGlobals`, `bslMetadata`, `bslQuery`, `bslDCS`, `snippets`) | 5.6 МБ | **+82 МБ** | 12 МБ |
| полная сборка | 10.6 МБ | **+100 МБ** | 16 МБ |

Отсюда раскладка одного экземпляра: **сам Monaco ~44 МБ**, **наша обвязка (провайдеры `bsl_helper`,
UI, дерево переменных, создание редактора и модели) ~38 МБ**, **языковые словари ~19 МБ**.

Разбор heap-снимка (после init, 495 тыс. узлов, 40 МБ):

| Что | Размер |
| --- | --- |
| `ExternalStringData` (исходник бандла в памяти V8), один узел | 16.4 МБ |
| прочие внешние строки | 2.1 МБ |
| code (bytecode + instruction streams + метаданные) | 7.6 МБ |
| строки | 4.7 МБ |
| shapes/maps/descriptors | 2.2 МБ |
| объекты, замыкания, массивы | 3.2 МБ |

Размер кода в бандле: Monaco 12.2 МБ (ядро `vs/editor` 6.0, `vs/base` 2.0, `vs/platform` 1.0,
крупнейший contrib — `inlineCompletions` 0.95), наш код 5.2 МБ (из них `bslGlobals.js` 3.2 и
`bslMetadata.js` 0.77). Итог: **основной вес — объём JS-кода и его компиляция**, а не данные
пользователя.

### 2.5. Что можно вернуть, не закрывая документ

| Действие | Эффект |
| --- | --- |
| `dispose()` сервиса справки | −178 МБ |
| dispose редактора, всех моделей, очистка Map-кэшей, снятие таймеров, чистка DOM | −10 МБ из 147 |
| навигация документа / закрытие вкладки | возвращается всё |

Вывод: **со стороны JS освободить базовые ~100 МБ невозможно** — их держат скомпилированный код и
внутренние структуры движка; они уходят только вместе с уничтожением документа (в Chrome — процесса
рендерера). Это и объясняет «1С не освобождает память при закрытии»: платформа не сносит контекст
webview.

## 3. Найденные утечки в сессии

1. **Модели diff.** `calculateDiff()` вызывается на каждое изменение текста (обработчик
   `onDidChangeModelContent`, debounce 50 мс) и делает
   `monaco.editor.createModel(window.editor.originalText)` без `dispose()` предыдущей — Monaco
   модели сам не удаляет. В пробнике число моделей росло 1 → 6 за несколько пачек правок; PoC-фикс
   (снимать прежнюю `original` после `setModel`) держит 2. Цена одной модели невелика (10 копий
   модуля 2.73 МБ дали +3 МБ — строки в V8 шарятся), но за часы работы моделей накапливаются сотни.
   Условие срабатывания: задан оригинальный текст (`setOriginalText`) и включены diff-декорации.
   **Подтверждено в поле A/B-прогоном (§2.0.1): 4.1 МБ на каждую правку текста, утёкших моделей
   ровно по числу правок.** Исправлено: `calculateDiff` больше не пересоздаёт original-модель,
   если оригинал и модель редактора не менялись (diff пересчитывается сам), а при реальной смене
   прежняя модель диспозится. После фикса — 81 правка, моделей по-прежнему 2, роста нет.
2. **`window.contextData`** (Map по номерам строк) и соседние кэши (`metadataRequests`,
   `selectedQueryDelimiters`, `reviewWidgets`) наполняются и не чистятся — `clear()` есть только в
   тестах. Рост медленный, но неограниченный; попутно данные протухают после правок (ключ — номер
   строки).
3. Временные модели в `updateText`/`insertLine`/`generateSnippetEvent` (`createModel` ради
   `getFullModelRange()`) не диспозятся — по одной на вызов. Исправлено вместе с п.1.

## 4. Гипотезы: на что мы можем повлиять

Порядок — по отношению «эффект / стоимость».

### Уровень A. В коде редактора

| # | Что | Ожидаемый эффект | Риск |
| --- | --- | --- | --- |
| A1 | Починить утечку diff-моделей (PoC готов) + диспозить временные модели в `updateText`/`insertLine`/`getDifferences` | убирает линейный рост в сессии | низкий |
| A2 | Ленивые словари: `bslGlobals` и соседи хранить строкой JSON и парсить при первом обращении; `bslQuery`/`bslDCS` — только в режиме запроса/СКД | до −19 МБ на консоль, которую открыли и не трогали; часть возвращается при первой подсказке | средний, трогает горячий путь подсказок |
| A3 | Ревизия contrib Monaco (`inlineCompletions` 0.95 МБ, `stickyScroll`, `colorPicker`, `gotoSymbol`, `dropOrPasteInto`, `unicodeHighlighter`) | оценочно −5…15 МБ | средний: часть фич используется (AI-подсказки, переход к определению) |
| A4 | Ограничить кэши (`contextData` и соседи): чистить при `setText`/смене модели | останавливает медленный рост | низкий |
| A5 | Экспортировать `disposeConsole()` (редактор, модели, воркеры, таймеры, кэши) | −10…20 МБ + предсказуемое состояние перед закрытием | низкий |
| A6 | Не создавать `query_model_worker` (829 КБ кода строкой + свой изолят), пока не открыт режим запроса | единицы МБ | низкий |
| A7 | Вывести на `window` выгрузку справки (`disposeHelp()`) — актуально только если справкой пользуются | −178 МБ при загруженной справке | низкий |

A1 **сделано** (§2.0.1). Приоритет остального по итогам полевого замера:
**A7/настройка справки** (763 МБ, если справкой пользуются) → **A4** → остальное. A2/A3 бьют по
базовым 329 МБ и дадут единицы процентов — заниматься ими имеет смысл после A1.

### Уровень B. На стороне интеграции (самый большой рычаг)

| # | Что | Ожидаемый эффект |
| --- | --- | --- |
| B1 | Один экземпляр консоли на приложение: переиспользовать открытую форму вместо новой | ~180 МБ на каждый несозданный параллельный экземпляр (замерено, §2.0) |
| B0 | Выключить автозагрузку синтакс-помощника, если справка не нужна | **−763 МБ на экземпляр** (замерено, §2.0) — самый дешёвый и самый крупный рычаг |
| B2 | Перед закрытием формы звать `disposeConsole()` | освобождает модели/воркеры/DOM даже если платформа держит webview (но не сам код — см. §2.5) |
| B3 | Проверить, сносит ли контекст переустановка содержимого поля (`Документ.location = "about:blank"` или очистка реквизита `HTML`) перед закрытием формы | если да — возвращается почти всё, это главный ответ на «1С не освобождает» |
| B4 | Держать `build:pack` (2.74 МБ), а не `build:single` (9.4 МБ) | HTML лежит в реквизите формы строкой (в 1С UTF-16, то есть ×2) и живёт в кэше формы на клиенте и сервере: экономия ~13 МБ на экземпляр только в памяти 1С |

### Уровень C. Вне нашего контроля

Базовые ~100 МБ (Chrome) / 200–300 МБ (WebKit 1С) — цена Monaco 0.55 в отдельном документе.
Существенно ниже — только переходом на принципиально более лёгкий редактор либо на один общий
экземпляр (B1).
